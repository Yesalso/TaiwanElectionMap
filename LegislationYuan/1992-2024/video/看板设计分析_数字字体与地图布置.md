# 看板設計分析：得票率／得票數／席次／字體／地圖佈置

> 分析對象：`Mayors/2022NineInOne/board/`（22 場縣市長 ＋ 1 場全國，設計座標 2560×1440，輸出 3840×2160）
> 方法：直接讀渲染真值 `src/engine/js/core/layout.js`、`core/theme.js`、`render/layers.js`、`headless.js`，以及排版求解器 `src/tools/_gen_boards.py`、驗證器 `src/tools/verify_layout.py`；實測數字取自 `dist/boards/*/layout.json`（23 份報告）
> 姊妹文件：`board/看板设计评审与经验总结_2026-11-19.md`（整版評審）、`board/NATIONAL_BOARD_EXPERIENCE.md`（全國場素材管線）
> 本文只講五件事：**得票率、得票數、席次、字體、地圖**，以及「地圖如何不互相碾壓」的具體機制。
> 撰寫日期：2026-11-19

---

## 0. 一句話結論

**這套看板把「數字」拆成三層（率＝主色大字、票＝白字富文本、席次＝實色牌匾），把「地圖」從固定框改成「框＝圖」的約束求解，並用 alpha 墨跡而非矩形來判定碰撞 —— 前者讓 22 個寬高比差 3.8 倍的縣市共用一套引擎，後者讓「框沒撞、墨跡撞」這種肉眼災難變成建置失敗。**

真正值得抄的不是那組座標，而是三個決策：

1. **數字大小由「讀者先看什麼」決定，不由「哪個數字更重要」決定** —— 得票率 128px 壓過姓名 104px，是這版最明顯的層級錯位（見 §2.4）。
2. **席次永遠不進照片位** —— 牌匾獨立、純數字、直角無框。這是被改了四輪才定下來的（見 §4.4）。
3. **地圖排版是可求解的約束問題，不是美工微調** —— 一旦寫死框，就會長出 `*_OFF` 例外表；一旦用矩形判定，就會漏掉墨跡（見 §6、§7）。

### 1.2 三層的分工鐵律

| 層 | 承載 | 視覺手段 | 不靠什麼 |
|---|---|---|---|
| 率 | 「贏多少」 |  **政黨亮色** ＋ 最大字 ＋ 同色光暈 | 不靠白字，避免與姓名搶 |
| 票 | 「有多少人」 | 數字大／單位小 ＋ 白 0.92 | 不靠顏色，靠**富文本分段** |
| 席 | 「拿到幾個位子」 | **實色牌匾** ＋ 純數字 ＋ 無描邊 | 不靠放大字級（牌是容器） |

**關鍵觀察**：三個層級用三種不同的「強調工具」——率用顏色、票用字級差、席用形狀（色塊）。這是它能在同一張板子上塞 11 個政黨／12 位候選人還不亂的原因。如果三者都用「放大字」，主卡會變成三團互相打架的大字。

## 2. 得票率（%）的設置

### 2.1 主卡：128px 政黨亮色、置中、帶光暈

```js
// layout.js
pct: { size: 128 },
lead: { nameToPct: 186, pctToVotes: 104 },
candidateBlock.pct.y   = candidateBlock.name.y + candidateBlock.lead.nameToPct;   // 1096+186 → 1282
candidateBlock.votes.y = candidateBlock.pct.y  + candidateBlock.lead.pctToVotes;  // 1282+104 → 1386
```

```js
// layers.js CandidateLayer
ctx.shadowColor = U.alpha(th.light, 0.5);   // 用政黨亮階做光暈
ctx.shadowBlur  = 36;
ctx.shadowOffsetY = 7;
U.text(ctx, c.pctText() + '%', {
  x: cx, y: conf.pct.y, size: conf.pct.size, weight: 900,
  family: NT.FONT_NUM, color: th.light, align: 'center', baseline: 'alphabetic'
});
```

三個決策值得記住：

1. **% 不與姓名同色**：姓名純白、率用 `theme.light`（KMT `#5f96ea`／DPP `#4fc47c`／TPP `#00d9ca`）。同一張卡上「人是白、票是藍／綠」，視線自然分成兩件事。
2. **光暈比文字陰影重要**：底色是街景照片（`dim 0.50`），純陰影（黑）會讓亮色數字變髒；用**同色光暈** 0.5 / blur 36 反而把數字從背景「浮」起來。
3. **基線定位而非框定位**：`pct.y` 由 `name.y + lead` 推導，改姓名字級不會移動率的基線（但會改變 cap-height 的視覺重心，見 §5.4）。

### 2.2 三個位置的三种寫法

| 位置 | 字級 | 對齊 | 顏色 | 為什麼不一樣 |
|---|---|---|---|---|
| 主卡 | 128 | center | `theme.light` ＋ 光暈 | 唯一的「主角級」數字 |
| 第 3 名高卡 | 62 | **right**（貼文字欄右緣） | `theme.light` | 與票數右緣對齊成一欄，讀起來像表格 |
| 小卡 | 32 | left | `theme.light` | 與姓名／副行／票數同一左起點 |
| 清單格 | — | **不印%** | — | 小黨的 % 已無資訊量（0.02%），只留票數 |

### 2.3 格式：固定兩位小數，一律帶 %

```js
// model/election-model.js
Candidate.prototype.pctText = function () { return this.pct.toFixed(2); };
// 繪製端一律 c.pctText() + '%'
```

- 好處：小數位對齊，`50.14 / 41.57 / 6.19` 三位一眼可比。
- 代價：**0.00% 也會印出來**（全國場 `oth9 0.0`、`oth10 0.0`）。看板上出現「0.00%」在語意上是錯的（他有票），建議改成 `<0.01%` 或直接省略 %（清單格已經這樣做）。
- `pct` 由資料層算好寫進 `meta.json`（`round(votes/total*100, 2)`），渲染端不再做除法 —— 分母口徑（區域票／政黨票／含原住民）的爭議全部關在資料層，這是對的。

### 2.4 這版最大的層級爭議：128 > 104

得票率 128px **大於**姓名 104px。視覺結果是「62.42%」比「蔣萬安」更醒目。

- 主敘事應該是「誰當選」，% 是佐證；現在的階梯讓佐證變成主體。
- 建議（不改引擎、只改兩個數）：`pct 112 / name 112`，或 `pct 108 / name 120`。若要保留「率很大」的氣勢，至少讓姓名 ≥ 率。
- 反例警示：**小卡更誇張** —— 率 32／名 27（1.19 倍）、**高卡 62／50（1.24 倍）**。這不是個別失誤，是一條一路沿用下來的比例。若整批要改，三個位置要一起改（`pct.size`、`minors.pctSize`、`minors.big.pctSize`），否則大小卡會看起來不是同一套。

## 3. 得票數的設置

### 3.1 富文本：數字 80 / 漢字 43

```js
// layout.js
votes: { size: 80, cjkSize: 43 }   // 比值 0.54
```

```js
// layers.js drawVotes —— 主卡、高卡、小卡、清單共用同一支
function drawVotes(ctx, c, x, conf, align, style) {
  var parts = U.voteParts(c.votes);         // "95萬9302票" → 數字段/漢字段
  var segs = parts.map(function (p) {
    return { text: p.text,
             size: p.num ? conf.size : (conf.cjkSize || conf.size * 0.55),
             weight: p.num ? 900 : 700 };
  });
  U.richText(ctx, segs, { x: x, y: conf.y, align: align,
    baseline: 'alphabetic', family: NT.FONT_NUM,
    color: (style && style.color) || '#fff',
    shadow: { color: 'rgba(0,0,0,0.55)', blur: 14, y: 4 } });
}
```

**分段的價值**：`576萬1851票` 若同字級，會變成 11 個等重的字，眼睛要從頭數到尾才知道量級。分段後「576」與「1851」大，「萬」「票」小 —— 讀者先抓量級（576 萬），再抓尾數，最後才是單位。這是中文票數排版最划算的一招，成本只是 `voteParts()` 一個 12 行的迴圈。

### 3.2 萬進位規則（會直接影響寬度）

```js
// utils.js
Utils.voteWan = function (n) {
  var v = Math.round(n);
  if (Math.abs(v) <= 10000) return String(v);      // 10000 以下 → 原樣，不加千分位
  var wan = Math.trunc(v / 10000);
  var rest = Math.abs(v % 10000);
  if (rest === 0) return wan + '萬';
  return wan + '萬' + ('000' + rest).slice(-4);    // 959302 → 95萬9302
};
```

| 輸入 | 輸出 | 備註 |
|---|---|---|
| 8,420 | `8420` | 不加千分位逗號 |
| 10,000 | `10000` | 邊界值仍走原樣 |
| 95,302 | `9萬5302` | 尾數補足 4 位 |
| 959,302 | `95萬9302` | 尾數補足 4 位 |
| 5,761,851 | `576萬1851` | 尾數補足 4 位 |

- **補足 4 位**（`'000'+rest`.slice(-4)）是刻意的：`9萬5302` 而非 `9萬5302`／`9萬302`。固定 4 位讓「萬以下」永遠是 4 個字元，寬度可預期。
- **不加千分位**是對的（中文語境用「萬」分段），但要注意：**清單格裡 `1,851票` 的註解與實際輸出不符**（`layers.js` 註解寫 `- 姓名 1,851票`，實際 `voteWan` 出來是 `1851票`）。文件與程式碼不一致，是這種「小工具函式」最常見的漂移。

### 3.3 顏色與對齊：用顏色做層級，不用字級

| 位置 | 顏色 | 對齊 | 意圖 |
|---|---|---|---|
| 主卡 | `rgba(255,255,255,0.92)` | center | 只比姓名略暗，支撐「人 > 票」 |
| 高卡／小卡 | `textDim`（0.66） | 右／左 | 票數退到第三層 |
| 清單格 | `textDim`（0.66） | **右對齊成欄** | 像表格，方便逐列比較 |

`theme.js` 只給三個白階（`#fff` / `.66` / `.40`），**沒有第四階**。這是好設計：超過三階人眼就分不出「哪個比較重要」，只會覺得「怎麼有些字灰灰的」。

### 3.4 量測陷阱：不要用「字數 × 字級」估寬

```js
// layers.js —— 量文字一律走這條
lineWidth(ctx, text, size, weight, spacing, family) → U.measureSpaced(...)
// 塞不下時
fitLine(ctx, text, size, weight, spacing, maxW) → U.fitText(...)（截斷補 …）
```

- 中文黑體的字面寬不是 1em（源石黑體約 0.98–1.02em 浮動），數字在 `Noto Sans UI Black` 下更是寬體。用字數估寬，在 `fit` 迴圈裡會**不收斂**。
- 實際踩過的坑：小卡加寬 4px 就讓 L8（越界）報警 —— 因為 `fit` 是線性估計，`w` 一改，`gap` 也得跟著改。結論：**寬度有上限時，改 gap 不要改 w。**

## 4. 席次的設置（三種形制 + 一段演化史）

席次只在全國場出現（`candidates[].seats` 有值才畫），但它是整套看板裡被改最多次、也最值得抄的部分。

### 4.1 形制一：主卡姓名左側的「牌匾」（最終版）

```js
// layers.js CandidateLayer
pH    = Math.round(nm.size * 0.86);        // 104 → 89
pW    = Math.round(pH * 1.34);             // 89 → 119
pGap  = Math.round(nm.size * 0.22);        // → 23
py    = nm.y - nm.size * 0.38 - pH / 2;    // 對齊姓名的視覺中心（CJK 字身中心）
ctx.fillStyle = th.main;  ctx.fillRect(gx, py, pW, pH);   // 直角、無描邊
seatBadge(ctx, gx, py, pW, pH, c.seats, { numSize: pH * 1.05, cjk: false, plaque: true, ink: th.dark });
```

| 參數 | 公式 | 104px 姓名下的實值 |
|---|---|---|
| 牌高 | `0.86 × 姓名字級` | 89 |
| 牌寬 | `1.34 × 牌高` | 119 |
| 數字級 | `1.05 × 牌高` | 93 |
| 牌↔姓名間距 | `0.22 × 姓名字級` | 23 |
| 垂直位置 | `name.y − 0.38em − pH/2` | 對齊字身中心，不是基線 |
| 形狀 | `fillRect` 直角、**無描邊** | — |
| 內容 | **純數字**（`cjk:false` 不印「席」） | — |

**最關鍵的耦合**：姓名可用寬度會被牌匾吃掉。

```js
maxNameW = Math.min(nm.maxW || 492, conf.card.w || 452) - (pW + pGap);
// 452 − (119 + 23) = 310
```

姓名從 452 的可用寬掉到 **310**，`nameScale = 310 / naturalW` 自動縮字（下限 0.4），仍超才 `fitText` 截斷。所以「加牌匾」不是純加法，是**跟姓名搶寬度**；這也是為什麼牌寬只能 1.34×牌高，再寬姓名就會明顯變小。

### 4.2 形制二：小卡照片下方的「席次條」

```js
var SEAT_BAR = { hRatio: 0.28, gapRatio: 0.05, minH: 22 };

// minorBlock：把方塊垂直切成兩塊，互不重疊
chipH  = max(22, round(m.h * 0.28));      // 160 → 43
chipGap = max(4,  round(m.h * 0.05));     // → 8
photoH = m.h - chipH - chipGap;           // 160-43-8 = 109（有席次時 blockH 先加到 m.h−8 = 152 → photoH 101）
// 席次條：th.dark 實色、直角、無描邊、數字 1.16×條高、基線下移 0.36em
numSize = chipH * 1.16;                   // 43 → 49.9
```

| 參數 | 值 | 作用 |
|---|---|---|
| 條高 | `0.28 × 方塊高`，下限 22 | 條永遠看得出是「另一塊」 |
| 條↔照片間距 | `0.05 × 方塊高`，下限 4 | 不壓照片的一條縫 |
| 數字級 | `1.16 × 條高` | 字身≈0.79h，視覺上幾乎吃滿條 |
| 基線 | `條中心 + 0.36em` | 大寫數字在條內真正居中 |
| 底色 | `theme.dark` | 比 `main` 暗一階，牌匾（main）與條（dark）拉開層級 |

**兩處常數必須同步**：`minorBlock()`（畫）與 `seatPhotoW()`（量）都要用同一組 `SEAT_BAR`。原本各寫一份，改一個忘另一個 → 量到的寬度與畫出來的對不上，`verify_layout` 用錯矩形。這是本專案「改渲染必須同時改量測」紀律的第一個實例。

### 4.3 形制三：色卡中央的「N 席」（已淘汰）

```js
// seatBadge 的一般模式（非 plaque）
numSize = opt.numSize || Math.min(w * 0.52, h * 0.42);
cjkSize = opt.cjkSize || numSize * 0.34;      // 印「席」
// 三遍迴圈：塞不下就等比縮（areaW / lineW）
```

這是 v1 的寫法：把席次直接畫進 452×620 的色卡中央。它被否掉的理由很簡單 —— **色卡是照片位**，數字畫進去，後製貼照片時就得挖掉。形制一、二之所以成立，是因為「牌匾在色卡外」「席次條在照片下」，兩者都保證 `照片區 = 乾淨的矩形`。

### 4.4 演化史（四版，看需求如何逼出最終形態）

| 版本 | 需求 | 結果 | 為什麼被改 |
|---|---|---|---|
| v1 | 席次畫進色卡中央 | 壓到照片位 | 後製無法貼照片 |
| v2 | 牌匾獨立、帶 ✓ | 數字被迫變小 | 勾牌吃掉牌寬（`areaW = w − cs − cGap − 14`） |
| v3 | 去掉 ✓、放大數字 | 數字 1.05×牌高 | 勾的語意冗餘（席次本身就是「贏」） |
| v4 | 席次條移出照片、直角、去「席」字 | 最終形態 | 「席」字對內行是廢話，對外行佔位 |

> 每一次「再加一點資訊」都讓主體變小。最終版能成立，是因為它做了**減法**：去勾、去框、去「席」字、去圓角。這是排版裡最反直覺的一條 —— 牌匾的價值不在它裝了什麼，在它**空出來的面積讓數字可以很大**。

### 4.5 三位數的風險（立法院場必踩）

`pW = 1.34 × pH` 是為 1–2 位數設計的。2024 立法院是「113 席」、早年是「161／164／225 席」：

- 牌寬固定 119、數字級 93 時，`113` 的實測寬約為 `14` 的 1.55–1.7 倍 → 會超出牌面。
- 現有 `seatBadge` 有「三遍縮字」保底（`areaW/lineW`），所以**不會溢出，但會縮字** —— 三位數的數字級可能掉到 70 上下，跟二位數的 93 不是同一個視覺重量。
- 正解（依成本）：①牌寬按字數參數化（`pW = f(位數)`）；②三位數屆別改用「數字 0.95×牌高 + 牌寬 1.5×pH」；③直接改成 §4.2 的橫條形制（條是橫的，寬度彈性大）。

## 5. 字體系統

### 5.1 字型堆疊：一支中文黑體 ＋ 一條長退路

```js
NT.FONT_STACK = '"GenSekiGothic TW H","源石黑體 H","GenSekiGothic TW",' +
  '"源石黑體","GenSekiGothic TW TTF Heavy","GenSekiGothic TW TTF",' +
  '"Microsoft JhengHei","Noto Sans TC","PingFang TC",' +
  '"Heiti TC",system-ui,Arial,sans-serif';

NT.FONT_NUM = NT.FONT_STACK;                                  // 數字沿用同一支
NT.FONT_DISPLAY_NUM = '"Noto Sans UI Black",' + NT.FONT_STACK; // 只給「標題級數字」
```

- 主力 `GenSekiGothic TW H` weight 900（源石黑體 TW Heavy）—— 筆畫粗、字面方正，適合遠看。
- 退路寫到 10 支，是為了**換機器不掉字**（Windows／macOS／CI 三邊字型不一樣）。只要第一支存在，輸出就穩定；不存在時逐字往下掉，不會變成豆腐塊。
- `FONT_DISPLAY_NUM` 只有日期塊（年份 96 / 日期 36）在用 —— 那是唯一需要「西文黑體寬字面」的地方。

### 5.2 「只換數字、中文不動」的 opt-in 手法

需求是「阿拉伯數字都用 2022 那支字型」，做法不是去改幾十個繪製點，而是在**定義衍生常數之前**改堆疊：

```js
// theme.js —— 這個 if 必須在 FONT_NUM / FONT_DISPLAY_NUM 之前
if (BOARD.meta.figures === 'display' &&
    NT.FONT_STACK.indexOf('Noto Sans UI Black') < 0) {
  NT.FONT_STACK = '"Noto Sans UI Black",' + NT.FONT_STACK;
}
```

原理：`Noto Sans UI Black` **沒有中文字身** → 數字／英文走它，中文逐字掉回源石黑體。等於免費得到「數字換字型、中文不動」。

三個工程細節值得抄：

1. **`indexOf` 防重複疊層** —— 重複前置會讓堆疊越長越肥（雖然結果一樣，但 `--report` 會看到髒資料）。
2. **順序敏感** —— 放在 `FONT_NUM` 定義之後就完全無效（衍生值已定型）。
3. **不宣告就完全不變** —— 22 場縣市長看板沒有 `figures` 欄位，輸出逐位元組不變。這是「opt-in 才敢共用引擎」的標準範式。

> **PIL 場的等價做法**（立法院看板 2026-11-19 已實作）：
> Pillow 沒有 CSS 的逐字回退，只換 family 不會生效。`blank_board.Board.text()`
> 改成把字串切成「數字段／非數字段」，各用各的字型量寬、逐段推進，
> 垂直方向先換算成基線再落字（`a → y+ascent`、`m → y+(ascent−descent)/2`、
> `d → y−descent`），否則兩支字型 ascent 不同，同一行會一高一低。
> 這也是「讓數字與中文分家」在 canvas 與 PIL 上唯一的共同解。

### 5.3 字重分工：900 與 700 只有兩級

| 字重 | 用在哪 |
|---|---|
| **900** | 姓名、得票率、政黨名、標題、席次數字、票數數字、清單姓名 |
| **700** | 副行、頁眉數據、票數的「萬／票」、席次的「席」、清單票數 |
| 600 | `layout.js` 宣告了 `stats.weight: 600`，但 `layers.js` 實際寫死 700（**文件與程式碼不一致**） |

只有兩級是對的：900 = 「事實」（誰、幾 %、幾票、幾席），700 = 「註解」（單位、副行、標籤）。第三級在這個尺寸下看不出差別，只會讓字型回退時更不穩。

### 5.4 基線與視覺中心：`0.38em` 這個數

```js
// 中文的視覺中心不在 middle，也不在基線
nm.y - nm.size * 0.38      // 席次牌、當選印記對齊姓名的「字身中心」
baseY = numTop + numSize * 0.86   // 大寫數字在牌內垂直居中的基線
seatChip: y + h/2 + numSize * 0.36  // 席次條內的數字
big.capRatio = 0.72         // 高卡：alphabetic 基線 = 行頂 + 字級 × 0.72
```

- CJK 字身大致落在 `baseline − 0.88em ~ baseline + 0.12em`，視覺中心約 `baseline − 0.38em`。
- 拉丁大寫高度約 `0.72em`，所以「行頂 + 0.72×字級」≈ 視覺中心。
- 這些魔數**不能統一**：中文用 0.38、拉丁用 0.72／0.86／0.36。硬要統一，結果就是「牌匾比姓名高半個頭」或「數字在條裡偏下」，而且只在某些字型下看得出來（最難查的一類 bug）。

### 5.5 字距：只在「大字」加

| 元素 | spacing | 為什麼 |
|---|---|---|
| 主標題 | 6 | 大字要透氣 |
| 姓名 | 6（隨字級等比縮） | 104px 不加字距會黏成一塊 |
| 政黨名 40 | 0 | 膠囊已置中，加字距會撐爆 |
| 小卡姓名 27 | 2 | 小字加太多會散 |
| 清單 26 | 1 | 表格化，字距要收斂 |
| 日期 36 | 5 | 與年份對齊節奏 |

**字距隨字級等比縮**是必要條件：`nameSpacing = sp * nameScale`。若只縮字級不縮字距，超長名縮到 0.7 倍時字距還是 6，看起來會「字小了但縫變大」。

### 5.6 陰影是「抗背景」手段，不是裝飾

底色是街景照片，白字必然帶陰影：

| 元素 | shadow |
|---|---|
| 姓名 | `rgba(0,0,0,0.65)` blur 22 y6 |
| 得票數 | `rgba(0,0,0,0.55)` blur 14 y4 |
| 得票率 | **政黨亮色 0.5** blur 36 y7（不是黑） |
| 副手行 | `rgba(0,0,0,0.5)` blur 12 y3 |

規律：**白字用黑陰影，彩字用同色彩光**。反過來做（彩字配黑陰影）會讓亮色變濁；白字配白光則完全失去邊界。

同一個道理延伸到「半透明白」：小卡副行預設 `textFaint(0.40)`，貼在街景上幾乎讀不到 —— 全國場逐場提到 0.86 才成立。**透明度的下限由背景決定，不由設計稿決定。**

## 6. 地圖佈置：從「固定框」到「約束求解」

### 6.1 座標環境

| 常數 | 值 | 含義 |
|---|---|---|
| `MAP_ENV` | `x 560, y 196, w 1444` | 可用區；右界 2004 = 右主卡左緣 2024 − 20 |
| `MAP_TOP_SAFE` | 236 | 頁眉下緣（鄉鎮圖不得高過此線） |
| `MAP_BOTTOM_SAFE` | 1092 | 小卡帶上緣 1102 − 10 |
| `MAP_BOTTOM_TALL` | 1230 | 左右並排時，村里圖可下探到的線 |
| `MAP_GAP` | 36 | **兩圖之間的固定淨空** |

五條水平線（236 / 1092 / 1102 / 1230 / 1396）就是整張板的骨架。地圖只能活在 196–1092（安全）或 196–1230（村里圖特權），**沒有任何一張圖可以跨過 1102**。

### 6.2 contain 公式（四行，決定了所有「不變形」）

```js
var s = Math.min(box.w / img.width, box.h / img.height) * (box.scale || 1);
var w = img.width * s, h = img.height * s;
var x = box.x + (box.w - w) * (box.anchorX ?? 0.5) + (box.dx || 0);
var y = box.y + (box.h - h) * (box.anchorY ?? 0.5) + (box.dy || 0);
ctx.drawImage(img, x, y, w, h);
```

- **不變形**（等比）由 `Math.min` 保證；`scale < 1` 才是「整體縮小」，`anchor` 決定縮小後貼哪一邊。
- 圖層把落點記到 `assets.mapRect`，`headless.js` 再換算成看板座標 → 這是所有驗證的資料源。**沒有這個紀錄，就沒有自動驗證。**

### 6.3 `plan_maps()`：兩種擺法 × 一維搜索 × 三條約束

```
輸入：r1 = 村里圖寬高比、r2 = 鄉鎮圖寬高比、W = 可用寬、H = 可用高、gap = 36
對 mode ∈ {stack(上下), side(左右)}：
    對候選尺寸（以 4px 為步長掃一遍）：
        w1 = 主圖寬 → h1 = w1 / r1
        剩餘空間給鄉鎮圖 → w2, h2 = _cap_town(...)
        若通過 _ok(...) → 記下「兩張面積和」
取面積和最大的那一組
```

三條約束（`_ok()`）：

| 約束 | 值 | 用意 |
|---|---|---|
| 村里圖面積 ≥ 鄉鎮圖 × `VILLAGE_AREA_MIN` | **1.35** | 主圖必須明顯更大，不能變成「兩張一樣大」 |
| 鄉鎮圖長邊 ≥ 村里圖長邊 × `TOWN_MIN_REL` | **0.40** | 鄉鎮圖不能變成小貼紙 |
| 鄉鎮圖短邊 ≥ `TOWN_MIN_SHORT` | **200 px** | 再小就看不清楚（1× 像素） |

還有一條**隱式**約束藏在 `_cap_town()`：鄉鎮圖面積不得超過村里圖的 `1/1.35`。所以即使空間夠，鄉鎮圖也會被主動壓下來 —— 這是「主圖優先」寫進數學裡，而不是靠事後微調。

### 6.4 實測：22 場的框寬差 3.8 倍

| 場次 | 模式 | 主圖框 w×h | 主圖墨跡右緣 | 鄉鎮圖框 |
|---|---|---|---|---|
| 連江縣 | side | **345.3 × 1032** | 1292 | 534.7 × 700（x1469） |
| 臺北市 | side（inset 85） | 788.3 × 1032 | 1427 | 534.7 × 700（x1469） |
| 彰化縣 | side（`MAP_TALL_OFF`） | 904.6 × **896** | 1457 | — |
| 金門縣 | **stack** | **1324 × 613.1** | 1933 | 533.2 × 246.9（y845） |
| 臺中市 | stack | 1264 × 613.7 | 1902 | — |

同一個模板、同一組約束，長出了 345 到 1324 的框寬 —— **這就是「約束」取代「固定框」的價值**。舊版兩套固定框讓苗栗只用到 43% 寬，總面積少 12%。

### 6.5 圖例與第二張圖：一格只能有一個主人

```js
// layers.js Map2Layer
if (L.legend && !L.legend.disabled && bx.allowWithLegend !== true) return;
```

- 22 場縣市長：`legend.disabled = true` → 右欄（1580–2004）讓給鄉鎮圖。
- 市長場若開圖例：圖例獨佔 1626–1978 × 493–933，鄉鎮圖**預設不畫**。
- 全國場：圖例搬到頁眉（`allowInHeader: true`，x1600 y62 w480 h118），與地圖框完全不重疊 → 用 `allowWithLegend: true` 放行第二張圖。

**規則本身很簡單：一欄只裝一個東西，要裝兩個就必須先證明它們的矩形不相交。** 這條規則是 2018／2022 臺北市「圖例壓掉內湖／南港／信義／文山」之後才補上的。

### 6.6 底板（plate）：可選、預設不畫

```js
Layout.map.plate  = null;   // 22 場：不畫
Layout.map2.plate = null;   // 22 場：不畫
// 全國場：{ pad, radius: 18, fill: 'rgba(5,9,24,0.55)' }
```

- 縣市圖是「單張不透明平面」，四周本來就有海面／留白，透出街景照片反而有層次 → 不加底板。
- 全國圖是「兩張高密度地圖並排」，海面透出照片會讓細邊界消失 → 加一塊暗板托住。
- **曾經加過、又拿掉**：底板太透 → 地圖透出街景樹叢；底板太實 → 跟白字糊成一片。結論是「要嘛不畫，要嘛畫得夠暗」；`rgba(5,9,24,0.55)` 是折衷值。

## 7. 如何避免地圖互相碾壓（八條可操作規則）

這一節是全文最該被抄走的部分。「碾壓」在實務上有五種形態，對策各不相同。

### 7.1 五種碾壓形態

| # | 形態 | 實例 | 對策層級 |
|---|---|---|---|
| 1 | **圖 × 圖** | 村圖與鄉鎮圖重疊 | 框層（`plan_maps`） |
| 2 | **圖 × 墨跡** | 框沒撞，但直式圖的下探段撞到小卡 | 墨跡層（alpha profile） |
| 3 | **浮層 × 圖** | 圖例／輔圖壓在村里色塊上 | 欄位層（獨佔一欄） |
| 4 | **卡 × 圖** | 第 3 名高卡往上長，撞到地圖下半部 | 分段墨跡比對 |
| 5 | **資料 × 背景** | 去底演算法把 `#333333` 當底色挖掉 | 素材層（保護合法填色） |

### 7.2 八條規則

**① 框＝圖，不留白邊。**
不要「先給一個大框、再 contain 進去」—— contain 必然留白，留白就是「框與框互相接近卻沒有東西」的假淨空。`plan_maps` 直接算出「這張圖在這個位置的確切寬高」，框＝圖。

**② 兩圖之間只留常數淨空 36。**
淨空不能靠「看起來夠寬」，要寫成 `MAP_GAP = 36` 並在求解器裡扣掉。左右並排與上下堆疊都用同一個值 —— 一致性比「這兩個場次看起來剛好」重要。

**③ 用 alpha 墨跡框（>16），不要用落的矩形。**
直式地圖四周留白很多：臺北的 `drawn` 是 645–1433，但 `content`（墨跡）是 651–1427。差 6–7px 看起來不多，但換成金門（`drawn` 620–1944、`content` 631–1933）就是每邊 11px，而且框越寬、放大倍率越高，誤差同步放大。判定一律用 `content`。

**④ 對「會長高的元素」用分段墨跡（48 段 profile）。**
第 3 名高卡與「其他候選人」清單會往上長到 y1102，而地圖下半部（y1100 以下）墨跡只剩中間一小段（臺北 x≈1009–1280）。用整張外接框比，會把「卡片明明在空白處」判成壓到；用 48 條橫帶逐段比，才驗得準。

```js
var INK_BANDS = 48;                     // headless.js
for (y = 0; y < h; y++) {
  b = bands[min(47, floor(y * 48 / h))];   // 每帶記自己的 x/y 外接框
  for (x = 0; x < w; x++) if (alpha > 16) { 更新 bb 與該帶 bb }
}
```

**⑤ 先讓障礙物定位，再解地圖。**
順序是：頁眉（236）→ 主卡（`card.y 274`）→ 小卡帶（1102–1390）→ 比例帶（1396）→ **最後才是地圖**。地圖是唯一「可壓縮」的元素，所以它必須是最後被擺的。反過來做（先擺地圖再塞卡片）就會天天改地圖。

**⑥ 例外表是債，要收斂成約束。**
目前有兩個硬編碼例外：

```python
MAP_BAND_INSET = {"臺北市": 85}   # 村圖下探段窄，整組右移閃開左側 others 卡
MAP_TALL_OFF   = {"彰化縣"}       # 下探段幾乎橫貫全圖，只能把村圖壓回 1092
```

它們是 `verify_layout` 的 L9 抓出來的（不是看出來的）。正解是把它們變成 `plan_maps` 的一條「墨跡帶避讓」約束：用 `layout.json` 的 `map.content` 判斷下探段寬度，窄→平移、寬→限高。**新增縣市時就不會再現第三個例外。**

**⑦ 浮層只有兩種合法位置：框外，或明說壓在哪。**
- 圖例 → 移到框外（1580 之外），幾何上不可能相交。
- 輔圖／離島格 → 若一定要壓在主圖上，就在文件裡寫清楚覆蓋率（例：立法院場的輔圖壓住本島西北角約 37%），並在驗證器裡標成 `WARN` 而不是 `PASS`。
- 最糟的是「壓上去了但沒人知道」—— 2018／2022 臺北市的圖例就是這樣，出圖被肉眼抓到才發現。

**⑧ 素材層也會碾壓資料。**
去底時用「與底色差 ≤ 8」判底色，會把苗栗那塊 `#333333`（無黨籍 75% 階）當背景挖掉 —— 底色 `#323232` 只差 1。正解是先從 `color.txt` 收集**全部合法填色**當白名單：

```python
fg = ~close_to_bg | is_legal_fill
```

這條只會多保留像素、不會反吃背景，所以裁切框與版面都不變。**教訓：「與底色差多少」不是可靠的去底判據**，灰度圖尤其如此。

### 7.3 驗證器：把「不碾壓」變成 12 條斷言

| 編號 | 斷言 | 抓的正是 |
|---|---|---|
| L1 | 圖例不得與地圖**墨跡**相交 | 形態 3 |
| L2 | 圖例不得與地圖**框**相交（更嚴） | 形態 3 |
| L3 | 圖例不得與頁眉／票數帶／小卡／主卡各塊相交 | 形態 3 |
| L4 / L5 | 圖例在 contain 框內／框在畫布內 | 出界 |
| L6 | 小卡不得壓主卡的得票率／票數塊 | 「票數疊成亂碼」 |
| L7 | 小卡彼此不得相交 | 排布算錯 |
| L8 | 每張小卡落在帶（x0..x1）內 | 越界撞主卡 |
| L9 | 第 3 名高卡／清單格不得壓地圖**墨跡**（分段比） | 形態 4 |
| L10 | 第二張圖不得壓主圖墨跡（分段比） | 形態 1／2 |
| L11 | 第二張圖不得與圖例／頁眉／票數帶／小卡／主卡相交 | 形態 1 |
| L12 | 第二張圖完整落在畫布內 | 出界 |

**驗證器的三個設計要點**（比規則本身重要）：

1. **用 PNG 的 alpha 判定，不用矩形** —— 矩形只能證明「框沒撞」，alpha 才能證明「墨跡沒撞」。
2. **主卡不給外接框，逐塊拆開** —— 主卡是 274–1403 × 1967–2533 的長條，外接框會把「色卡右側的空白」也算成佔用，圖例一比就誤判。
3. **例外要顯式宣告** —— `legend.allowInHeader` 讓 L3 跳過頁眉判定；沒有這個旗標，全國場的「圖例擺頁眉」就永遠驗不過。**能宣告的例外，才是可維護的例外。**

## 8. 移植到「立法院看板」（`LegislationYuan/1992-2024/video/`）的對照

| 項目 | 2022 縣市長 | 立法院現況（README） | 建議 |

| 主角 | 人（姓名 104 > 率 128） | 黨（黨名 30 < 率 52） | **保留反轉**：不分區是「黨 > 票」，率大是對的 |

### 8.1 輔圖壓主圖：用 2022 的規則重新算一次

> **已於 2026-11-19 修正**：輔圖改成真正的離島三格、移到主圖東南海面 `(1100, 1014)`，
> 墨跡重疊從 20.8% 降到 0.31%（156 px，綠島／蘭嶼的小點）；兩張主圖也改成一鄉鎮級、
> 一縣市級。改動清單見 `README.md §十二`。以下保留當時的分析過程。

現況：主圖框 600×1084（比例 0.55），輔圖 280×350 浮在左上，覆蓋本島西北角約 37%。

用 2022 的三條規則檢查：

1. **框 ≠ 圖**：600×1084 的框 contain 完，本島實際只有 **503 寬**（左右各空 48）。所以「輔圖 280 寬」壓上去的實際覆蓋率比用框算的更高。**淨空要用 `drawn`／`content` 算，不能用 `frame`。**
2. **浮層只有兩種合法位置**：框外，或明說壓在哪。現在是「明說壓在哪」—— 那就必須在驗證器裡記成 WARN，不能記 PASS。
3. **降級順序**（依成本，與 2022 的例外表同思路）：
   - ① 輔圖縮到 240×300（覆蓋 37% → ~28%）；
   - ② 移到主圖框右下（東南海面，本島墨跡在那裡本來就空）；
   - ③ 主圖 `anchorX` 右移到 0.9，讓出左帶（需渲染器支援 `anchorX`）。

> ② 是最乾淨的：它把「壓」變成「不壓」，代價只是輔圖的位置與草圖不同。2022 的圖例就是走這條路（從框內移到框外），一勞永逸。

### 8.2 多屆（161／164／225／113 席）的參數化

- **席次位數**：2 位（14）→ 3 位（113）→ 3 位（225）。牌寬 `1.34 × pH` 只對 2 位數成立。
- **政黨數**：2024 有 6 個有效政黨，早期更少 → 卡數與「其他政黨」列數都要能自動長（`others.maxH` 目前上限 268，超過就壓列高、縮字）。
- **地圖素材**：`1992.png` 那類「海報」左上角有大陸輪廓與圖例，**上板前必須先挖掉**（`CHINA_BOX` 整區 alpha 歸零，不能用裁切 —— 台灣最北端比大陸輪廓下緣還高，橫切會先切掉台灣）。
- **兩張主圖放什麼**：建議主圖 1＝鄉鎮市區級、主圖 2＝縣市級（同源同範圍，一張看細、一張看粗），與 2022 的「村圖＋鄉鎮圖」完全同構，可以直接套 `plan_maps` 的 1.35／0.40／200 三條約束。

## 9. 交付前檢查清單（數字與地圖各 6 條）

**數字**

1. 得票率是否固定兩位小數、是否出現「0.00%」（應改 `<0.01%` 或省略）。
2. 得票數是否走 `voteParts` 分段（數字 900／漢字 700），單位是否與資料一致（票／人）。
3. 萬進位是否補足 4 位（`9萬5302` 而非 `9萬302`）；10,000 邊界是否正確。
4. 姓名／率／票三者的字級階梯是否維持同一方向（率 ≤ 姓名 為佳）。
5. 小卡副行在街景上是否讀得到（`.40` → `.62~.86`）。
6. 超長名是否「先縮字級、仍超才截斷」，字距是否隨字級等比縮。

**地圖**

7. 每張圖的框是否等於圖（無 contain 留白）；淨空是否 ≥ 36。
8. 判定是否用 alpha 墨跡（>16）而非 `drawn` 矩形。
9. 會往上長的卡（高卡／清單）是否用分段 profile 比對。
10. 浮層（圖例／輔圖）是否「在框外」或「已記錄覆蓋率並標 WARN」。
11. 例外是否只有 `MAP_BAND_INSET` / `MAP_TALL_OFF` 兩個，且都有註解說明是 L9 抓出來的。
12. `verify_layout.py` 是否 23 份 0 未通過；重渲染臺北市 sha256 是否與基準相同（`72c1bfb4…`）。
