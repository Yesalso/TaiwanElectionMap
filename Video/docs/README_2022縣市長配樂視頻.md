時間軸公式（全部換算成 24fps 整數幀，避免小數累積漂移）：

- 第 k 個轉場 offset（幀）= `sum(幀數[:k]) − k × 12`；
- 成片總幀數 = `sum(幀數) − 22 × 12`；
- 第一張圖的幀數額外加上 `3.0s × 24 = 72` 幀作為靜音開場。

改動秒數後腳本會自動重算，不需要手動對齊影格。

每次重跑至少核對這五項：

| 項目 | 方法 | 合格標準 |
|---|---|---|
| 解析度／編碼 | `ffmpeg -i 成片.mp4` | `3840x2160 / 24fps / H.264 High / yuv420p` |

## 5. 經驗總結

### 5.1 4K 不是「放大」，是「不要先縮小」

`dist/final/2022` 的源圖（現成看板 PNG）已經是 **3840×2160**。腳本裡的
`scale=3840:2160:flags=lanczos` 只是統一尺寸／像素格式，不是把 1440p 拉大。
若先產 1440p 再放大到 4K，文字邊緣會糊掉，且無法補回細節。

### 5.2 片頭 3 秒靜音的正確做法

不是把音樂整體調小，也不是把前 3 秒樣本清零，而是：

1. 第一張圖的輸入幀數加 `3.0 × 24 = 72` 幀；
2. 音軌先 `atrim` 到畫面需要的長度；
3. 用 `adelay=3000|3000:all=1` 把音樂整體延後 3 秒；
4. 淡入濾鏡的起點寫 `st=3.0`（不是 `st=0`）。

這樣前 3 秒是真正的數位零，畫面仍停在全國圖；音樂第一個樣本精確落在 3.0s。

### 5.3 時間軸用「整數幀」，不要用四捨五入的小數秒

多段 `xfade` 會把每次轉場的重疊扣掉。若 offset 每次只保留小數點後 3–4 位，
22 次轉場可能累積出可見的漂移。改成：

```python
seg_frames  = round(每段秒數 × 24)
offset(k)   = (sum(seg_frames[:k]) − k × 12) / 24
total_frames = sum(seg_frames) − 22 × 12
```

所有 offset 都落在 24fps 的整數格上，最後總幀數固定是 **6160**，可重現。

### 5.4 為什麼預設改成 `fadeblack`

地圖看板文字密集，直接 `fade` 交叉淡化時，兩張圖的縣市名、數字會在半秒內
疊在一起，看起來像殘影。`fadeblack` 是「淡出到黑 → 從黑淡入」，
同一時間只會看到一張圖，對資訊型地圖更清楚。

仍保留 `--transition fade`，想要傳統交叉淡化時可直接切換：

```bash
"$PY" -X utf8 src/tools/make_2022_county_video.py --transition fade
```

### 5.5 4K 編碼與中斷處理

- 參數：`libx264 / crf 16 / preset slow / tune stillimage / yuv420p / AAC 192k`。
- 4K 的編碼時間約為 1440p 的 2–3 倍；用背景執行並把日誌寫到檔案，避免終端緩衝。
- 若編碼被中斷，`_raw_tmp.mp4` 會是沒有 `moov atom` 的半成品，`ffmpeg -i` 會報
  `moov atom not found`。**刪掉重跑**，不要試圖修復。
- 重跑前先確認輸出目錄沒有舊的 `_raw_tmp.mp4`，避免誤判為新檔。

### 5.6 質檢的兩個常見誤判

1. **容器時長 ≠ 畫面時長**：AAC 有編碼 priming/padding，容器可能比 6160 幀多幾十毫秒；
   應以畫面幀數為準，不要用 `Duration` 直接判定掉幀。
2. **不要用「偏移必須是 0ms」當標準**：AAC 解碼／重採樣通常有約 −5ms 的固定延遲。
   只要各段偏移一致、相關係數 > 0.99，就是正確對位。
3. **不要先把成片抽成 PNG 再比 SSIM**：多一次 YUV→RGB／limited→full 的轉換，
   會讓同一幀的分數從 0.998 掉到 0.97，誤判成圖片錯誤。應讓 ffmpeg 直接解碼成片，
   與源 PNG 在同一條濾鏡圖裡比較（本專案的 `verify_2022_county_video.py` 已這樣做）。
