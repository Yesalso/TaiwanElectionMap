## 一、事实核对：着色到底发生在哪（这次有代码为证）

以总统场地图脚本 `Precident/maps/Draw_Region_Maps_AllYears.py` 为例，逐行核对：

| 环节 | 代码位置 | 实际行为 |
|------|----------|----------|
| 决定每区颜色 | 第 780–794 行 | `name = max(rates, key=rates.get)` 找出该乡镇得票率最高的候选人 → `get_color_by_value(rates[name], RATE_COLOR_STOPS[gi])` 从 `color.txt` 色阶取色 → 写进 `fill_hex[i]` |
| 没数据的地方 | 第 85、789 行 | 填 `NO_DATA_COLOR = "#FFFFFF"`（纯白，即留白） |
| 烘到像素 | 第 576–604 行 `flood_fill_layer` | rasterio 把每个几何面的 `fill_hex` 栅格化 + 洪水填充，**直接写进 RGB 数组** |
| 落盘 | `plt.savefig` | 存成 `map.png` / `map2.png` 成品 |

结论：**颜色在 `Draw_Region_Maps_AllYears.py` 跑完的那一刻就已经定死，成为 PNG 的像素值。** 之后浏览器端 `MapLayer.draw` 只是 `drawImage` 把这张已上色的图贴进画布，运行时零着色。

同样，市长线 `Converge_to_map_taipei.py` 也是「读 xlsx → 填色 → 出 PNG」的同款流程，只是它明确 `只做臺北市`。

### 「只有新北需要」怎么理解才准确

你说「原本新北的需要」——精确的说法是：

- 新北**不是**「地图没上色、要运行时补色」的例外。
- 新北是**市长线脚本 `Converge_to_map_taipei.py` 主动排除的范围**：代码注释写死「只做臺北市，新北市（2014）不在本腳本的範圍內」，`boards/2014-newtpei-mayor/.skip` 也因此被 `--all` 跳过。
- 换句话说，如果哪天要做新北市长场，需要的是**补一个『读新北 xlsx → 着色 → 出 PNG』的 Python 脚本**（跟臺北同款），而**不是**把着色挪到浏览器运行时。

这与「PNG 里是否已上色」是两件独立的事，上一版把它们混为一谈了。

## 二、你的方案，套到现状 = 拆掉重做

方案的核心铁律是「**绝对不要把获胜颜色画到底图上，颜色必须在浏览器运行时叠加出来**」。

### 关键澄清：这 4 步不是「必须」，而是「仅当你要运行时上色」才出现

你问得很对——**既然背景街景图（`share/街景3.png`）可以你手动放进一张图、引擎直接贴上就用，那地图 PNG 为什么不能同样处理？**

答案是：**能，而且现状就是这么做的。** 地图和街景在本项目里是同一类东西：

- 街景 `street_bg.png`：`layers.js` 第 198 行 `ctx.drawImage(bg, ...)` cover 铺满 + 暗罩。
- 地图 `map.png`：`MapLayer.draw`（第 601–620 行）`ctx.drawImage(img, x, y, w, h)` contain 进框，**零着色逻辑**。

两者唯一的差别只是**这张图从哪来**——街景是你手动放的，地图是 Python 脚本算好色存出来的。但对引擎来说它分不清，都是 `drawImage` 贴上去。**所以：把地图当成「你手动提供的一张成品 PNG」完全成立，不需要任何额外操作。**

那么上一节列的「4 步」是什么？它们**不是给你『换候选人/得票/地图』用的**，而是**只有当你想要『运行时动态上色』（即前文方案里说的，让前端用 CSS/blend 实时改地图颜色、不再用 Python 出图）时才需要**。换句话说：

- **你的原始诉求（每张看板只换候选人/得票数/地图）** → 地图就是一张成品 PNG，像街景一样贴上去即可，**现状已经是这样，0 改动**。
- **你给的蒙版方案（运行时上色）** → 才需要下面这 4 步，因为它要的是「前端自己叠颜色」，而非「贴一张已上色的成品」。

下面 4 步是**针对『运行时上色』这个（大概率你们不需要的）场景**列的成本，不是现状的必做项：

1. 重出一张「黑底白轮廓、无任何获胜色」的**中性底图**（`north_base.png`）；
2. 重出**每一块行政区的透明蒙版**（区级 100+ 张乡镇、村里级 500+ 张）；
3. 把引擎从「贴一张成品 PNG」改成「贴底图 + 逐区 multiply 叠蒙版」；
4. 重新验证像素对齐、alpha 行为、导出捕获。

也就是说，只有在「非要在运行时叠色」这个前提下，**才需要先花大力气把『已经上好的色』洗掉、再在运行时把『同样的色』重新叠回去**。对「只想换候选人/得票数/地图」的诉求，这是负收益、也完全没必要。

## 三、唯一值得做的场景：你要「同一页面动态切换任意选举结果」

如果你们的真实意图是下面这一条，那方案才有意义：

> **不再用 Python 重画地图，改由前端在运行时用 JSON + 蒙版即时生成任意一届、任意结果的地图。**

现状确实做不到这一点：改一届 = 重跑 `Draw_Region_Maps_AllYears.py`（约 7 秒）重画地图。若你们将来要做「用户在网页上拖拽调整某个县市的赢家、地图实时变色」这类交互，运行时上色才刚需。

但即便要走这条路，也必须按台湾的粒度重拆，不能照巴西 27 州套：

- **粒度**：巴西 27 州；本项目是 4 县市 → 100+ 乡镇（区级）→ 500+ 村里（村里级主图）。
- **素材量**：村里级 500+ 张独立蒙版，逐个 `<img>` 请求会拖垮首屏，**必须走 sprite 雪碧图**（方案的「备选」在这里是「必需」）。
- **渲染路径**：方案默认 DOM 叠加（`map-wrapper` + 一堆 `<img>`），会连带打散现在跑顺的「CDP 无头截图 + `verify_layout.py` 自动验证」整条链路。贴合本项目应改成 **canvas 内 `globalCompositeOperation='multiply'`**，改动集中在 `MapLayer` + `slide.js`，渲染与验证链路基本不动。
- **色阶冲突**：现状地图是「**按票差深浅的 5 档色阶**」，方案是「**每区单一获胜色**」。若改成纯色会丢掉「票差越大越深」的信息量；要保留就得分档蒙版/着色，复杂度再上一阶。

## 四之补充：真正的架构问题 —— 为什么版式用 canvas 手绘，而不用 HTML/CSS 元素搭？

你后面点出的那个问题，比「地图上色」更根本，值得单独回答：

> 「看板不负责画地图，地图只做缩放/透明度处理；而且版式大部分位置每届都一样，那为什么这些固定版式不用前端 HTML/CSS 元素来搭，而非要用 canvas 图层手绘？」

**先纠正一个误区**（这部分之前分析没点透）：本项目的看板**确实不画地图**，`MapLayer.draw`（`layers.js` 第 601–625 行）对地图只做 `contain` 缩放 + `anchor` 定位 + `drawImage`，`Map2Layer` 同理——零着色、零绘制。地图就是一张成品位图，被当素材贴进画布，跟街景 `street_bg.png` 一模一样。

所以你的判断**对**：单看「搭版式」这件事，用 HTML/CSS（`position: absolute` + 固定坐标 + `<img>` 贴图）**完全能实现，而且更直观、更好改**。现状之所以选 canvas，**不是因为「地图必须 canvas」或「canvas 更对」**，而是因为三个跟排版无关、但决定工程形态的原因：

1. **最终产物是一张 PNG 海报，不是给人交互的网页。**
   看板要导出成 2560×1440 的 PNG（`render_boards.mjs` 用 Edge CDP 无头截图，`__saveBoard` 把 canvas `toBlob` 后 POST 给 Node 写盘）。canvas 的 `drawImage`/`fillText` 能被无头浏览器**精确、可复现**地转成像素——这是「导出 PNG」最稳的载体。HTML/CSS 也能用 html-to-image 截图，但多一层「DOM→位图」的转换，字号、间距、抗锯齿的像素级一致性更难保证。

2. **要「逐像素」自动验证版式，canvas 是像素本体，DOM 不是。**
   现有 `headless.js` 的 `alphaScan`（第 156 行）直接扫 canvas 里图片的 alpha 墨迹，算出**分段外接框**（`profile`），再交给 `verify_layout.py` 的 L1–L12 判断「图例有没有压到地图墨迹」「小卡有没有越界」「区级图有没有叠到主图」。这套「画布 → 像素 → 断言」的闭环，天然建立在「内容已经是一张像素图」的前提上。换成 DOM 叠加，就要靠 `getBoundingClientRect()` 去量每个元素的实际落点再换算，等于**重造一整套量测层**。

3. **字体墨迹宽度会反向决定版式，canvas 的 `measureText` 是这套逻辑的支点。**
   得票数/得票率这些数字的**真实墨迹宽度**决定「高卡要不要缩、文字要不要换行」（`headless.js` 第 204–223 行 `textWidth`/`votesWidth` 用真字型量宽），`headless.js` 第 48–68 行还专门「先画一次触发字体下载、等 `document.fonts.ready`、超时 3 秒」确保数字墨迹与正式版一致。HTML/CSS 不是不能做，但复刻这套「字级三层缩放 + 超宽自动缩」的成本会显著更高。

**一句话总结**：现状用 canvas 是**为了「像素级导出 + 逐像素自动验证 + 字体墨迹精确控版」这三个目标**服务的，跟「地图是不是成品图」无关。你的观察对——「搭版式」HTML/CSS 足够甚至更直观；但只要「最终交付是逐像素可验证的 PNG 海报」这个前提不变，canvas 反而是阻力最小的选择。**是否值得换成 HTML/CSS，取决于你是否愿意放弃/重写现在跑顺的自动验证链路**——那才是真正的代价所在，而不是「地图上不上色」。

## 五、结论与建议

1. **你的质疑成立，且是关键**：PNG 已经是着色成品，运行时上色是「拆了重做」，不是「补缺」。上一版「现状缺运行时上色、值得改」的判断要收回。
2. **唯一例外「新北」跟着色无关**：它是市长线脚本的范围取舍（只做臺北），补新北 = 补一个 Python 出图脚本，而不是运行时上色。
3. **要不要做，取决于一个分岔**：
   - 只要「每届换候选人/得票/地图」→ **现状已达标，不建议动**（改动是负收益）。
   - 要「前端运行时动态切换任意结果/交互改色」→ 方案才有意义，但须按台湾粒度重拆（蒙版走 sprite、渲染走 canvas multiply、想清楚是否保留票差深浅色阶）。
4. **建议下一步**：确认你们到底有没有「运行时动态改色/交互」的真实需求。若没有，这件事到此为止；若有，我再据此出一份精确到文件与函数的实施清单（含 sprite 生成脚本、canvas multiply 落点、`verify_layout.py` 的 L9–L12 需核对项）。
