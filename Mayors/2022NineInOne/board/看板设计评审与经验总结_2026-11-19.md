## 3. 設計評估

### 3.1 站得住的部分（不要動）

1. **單一真值源**：所有座標／字級／顏色集中在 `layout.js`＋`theme.js`，`meta.layout` 只開放 `legend / map2 / map / ribbon / minors` 五個區塊淺層覆寫。改版式不必碰 82KB 的 `layers.js`。
2. **對稱骨架**：`cx 310 / 2250` 左右鏡像、主卡 452×620、中段讓給地圖 —— 視線動線清楚：**人 → 票 → 地**。
3. **「框＝圖」的求解式排版**（`plan_maps()`）：不再寫死兩個固定框，而是依每場兩張圖的實際寬高比做一維搜索，取「兩張面積和最大 × 村里圖 ≥1.35 倍鄉鎮圖 × 鄉鎮圖短邊 ≥200」的解。實測 22 場框寬 **345（連江）～1324（金門）**，差 3.8 倍而不破版，這是整個專案最有價值的一條方法論。
4. **驗證器驅動**：L1–L12 用 PNG 的 alpha 墨跡分段判定「有沒有壓到」，比肉眼可靠；`MAP_BAND_INSET`／`MAP_TALL_OFF` 兩個例外就是被 L9 抓出來的。
5. **opt-in 擴展**：新增 `seats / leader / sub / header.stats / figures / subInk` 等欄位全部「宣告才生效」，所以全國場能長在同一套引擎上，而 22 場輸出逐位元組不變（sha256 相同）。

## 4. 骨架圖作為「文件」的保真度

這是本次評審最值得沉澱的一點：**骨架圖的價值 100% 取決於它能不能被當成真值，而它目前是「手抄＋局部美化」的混合體。**

- 抄對了的部分（01、02、04、06–08、11、13）覆蓋了 70% 的元素，數值可直接對照 `layout.js`。
- 抄偏的部分（09 寬度、12 帶寬、14 圖例位置、05 字級）剛好都是**「按畫面好看與否微調過」**的地方 —— 而這正是讀者最容易被誤導的地方。
- 三個文字塊「框比字小」是典型的「為了好讀而縮框」，但讀者會理解成「字級 104 卻只有 84 的空間」。

**根因**：`blank_board.py` 把 `layout.js` 的常數**複製**了一份（`HEADER_H / CARD_W / MAP / MINORS_Y / BIG / RIBBON_Y`）。複製就會漂移 —— 這和 README §3 踩過的「`dist/boards/<id>/board.js` 才是渲染真值」是同一類錯誤。

**正解（二選一）**：
1. **由引擎自己出骨架圖**：`layers.js` 加一個 `debugSkeleton` 開關，只畫框與編號，用同一套 `layout.js` 與 `headless.js` 量測 → 永遠不會漂。工作量小（一天內），且能順便產出全國場骨架。
2. **導出再讀**：`render_boards.mjs --report` 已經輸出 `layout.json`（含 `map.frame`／`elements` 全部矩形），`blank_board.py` 改成讀 `dist/boards/2022-taipei/layout.json` 畫框，只保留「標註文字」手寫。工作量更小，且天然等同「某一場的真實骨架」。

> 建議走 2：成本最低，還順帶解決「骨架圖只有一張、但每場框都不同」的表達問題 —— 可以一次出「預設框版 + 臺北版 + 連江版」三張，把 345～1324 的差距講清楚。

## 5. 經驗總結

### 5.1 版式層：三條可複用結論

1. **先定骨架，再定內容**。236 頁眉 / 274 主卡 / 910 膠囊 / 1096 姓名 / 1230 小卡 / 1396 比例帶 —— 這 6 條水平線一旦定下，所有元素都只是「掛在哪條線」。骨架圖最大的貢獻就是把這 6 條線可視化，建議把它升格為 `LAYOUT.md` 的配圖。
2. **固定框會背叛你，約束不會**。舊版兩套固定框（直圖 880＋右欄 564×700；橫圖 1430×470）讓苗栗只用到 43% 寬；換成「村里圖 ≥1.35×鄉鎮圖」這種**約束**後，框自己長出來，總面積 +12%。任何「一組數字套 22 個場次」的做法，最後都會留下一堆 `*_OFF` 例外表。
3. **對稱是為了掃視，不是為了美感**。左右主卡鏡像讓「藍 vs 綠」在 0.2 秒內可比；地圖居中、比例帶在底部，形成「人—票—地」的閱讀順序。不要為了塞更多資訊打破左右對稱。

### 5.2 工程層：五條紀律

1. **單一真值是唯一，複製即負債**。`layout.js`、`county_map.py`、`color.txt` 三個真值源各自只有一份；任何脚本「抄一份常數」都會在下次改版時說謊（本次骨架圖就是活例）。
2. **改渲染，必須同步改量測**。`layers.js` 與 `headless.js` 的矩形計算要一起動（P0-3 的印記尺寸、9.6 節的席次牌都是這個坑），否則 L3/L6 用錯矩形、驗證反而變成假通過。
3. **驗證器要能「看見墨跡」**。L9/L10 用 PNG alpha 分段判斷，才能抓出「框沒撞、墨跡撞」；純矩形比對抓不到。新元素（席次條、印記）都要納入 `elements` 回報。
4. **opt-in 才敢共用引擎**。新能力全部「宣告才生效」，並用 sha256 回歸（重渲染臺北市，`72c1bfb4…` 必須不變）守住 22 場。這是 23 場共用一套 `layers.js` 還能維持穩定的唯一原因。
5. **交付物與清單分離，但都要在盤上**。manifest 記 sha 是好事，但 `dist_png/2022/` 一空，交付就成了「一張清單」。建議每次定稿後打一個 `release/` 包並計算校驗檔。

### 5.3 工具層：兩個具體坑

- **PIL 半透明**：往 RGBA 圖上直接畫 `(255,255,255,26)` 是**覆蓋 alpha**，不是混合，存成 RGB 後半透明塊整塊變白（第一版 14 個編號牌全白）。正解：全部畫到獨立 RGBA 覆蓋層，最後一次 `alpha_composite`。
- **字型回退**：`gensekigothictw-heavy.ttf` 不在就退回 `msjhbd.ttc`，兩者字寬不同 → 骨架圖的標註換行位置會變。要嘛鎖字型，要嘛用 anchor 定位不要靠字寬推算。
